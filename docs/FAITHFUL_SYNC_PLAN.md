# Chatmode 可验证保真同步方案

状态：**用户已授权并开始离线实施；尚未交付、未部署，两个旧会话未恢复。** 当前实现及阻断见 [FAITHFUL_SYNC_IMPLEMENTATION.md](FAITHFUL_SYNC_IMPLEMENTATION.md)。

按最后范围确认，只推进这一套统一方案，不做两个 Agent ID 的独立热修；验收必须包含两条已失败原会话的历史对账、后续回传及控制状态。
日期：2026-10-17。宿主证据基于 Paseo 0.11.4、插件 SDK 0.11.2。

## 1. 目标与第一性原理

用户应该只看 Paseo 的 Agent 聊天界面，就能知道对应 ChatGPT 页面当前呈现了什么，并判断下一步。保真的是内容、身份、顺序和状态，不是网页像素/排版，也不是自动远程控制。

必须回答四个问题：

1. **网页实际呈现了什么？** 正文、公开过程、工具/媒体、错误原文及 Retry 等控件状态。
2. **它属于谁、什么时候的事实？** 对话、文档代次、用户锚点、原生消息/调用/资产 ID、来源位置和观察时间。
3. **哪些是已知，哪些没读到？** 空值不等于不存在，读取失败不等于网页执行失败，最后已知值不等于当前值。
4. **Paseo 展示和机器消费是否真的保留了这些事实？** 必须对账，不凭四个成功样例就宣布完整保真。

用户进一步澄清：信息维度保真不等于取消控制判断。CIP 同时承担两项职责：忠实采集/保存/呈现网页信息；依据明确证据完成投递确认、排队、停止确认及轮次收尾。Paseo/服务端插件、Chrome/扩展/页面脚本各自的运行状态，两端连通状态，以及发送与回传健康度都必须保留并准确展示。Provider可选或已配对，不等于扩展当前连通，更不等于回传正常。错误分类/解释不能替代网页原文；控制判断必须明确依据和不确定性。明确区分：

- ChatGPT 页面可见事实；
- 网页所报告的执行状态；
- CIP 的观察/同步健康度。

即使网页一轮回应结束，也不能据此宣称它调用的所有远程后台任务都已停止。

## 2. 先写清现实边界，不把诚实降级叫完整交付

### 已确认的宿主边界

原版 `plugin-provider.js:1338` 对 assistant 和 reasoning 全文只做“前缀 → 新增后缀”。若已发布“甲”，新全文修订为“乙”，会追加成“甲乙”，而不是替换。

原版 `agent-manager.js:2214` 只拼接最后连续的 assistant 段。因此界面整体文字正确，不保证工具穿插后的机器完成回报完整。

所以以下三项不能无条件同时保证：

1. 正文逐字实时（**最新授权已取消此要求，改为每条消息完结后整体提交**）；
2. 任意已发布字符的修订都能 1:1 回写；
3. 不改宿主、只使用现有原生正文接口。

当前没有证据证明现场首次错误一定是真实正文修订；不能预设模型改字。只增也不能被预设为所有页面表示的性质，它必须在选定规范来源后验证。

**本方案默认只改 CIP。**先修确定的采集缺陷与状态失真，不启动宿主修改、替代正文卡片、截图按钮、debugger 权限或 turnId 重构。如果严格完整保真需要目前不存在的正文替换/完整结果接口，必须带具体证据另行请用户决定；不能追加第二份全文、整轮停流或忽略修订来伪装通过。

### 实施前门禁

| 门禁 | 证据/状态 | 对方案的影响 |
| --- | --- | --- |
| 非前缀正文及公开摘要替换 | 原版代码及既有诊断已证实不支持 | 真实修订不能计为完整保真通过 |
| 工具穿插后的完整机器结果 | 已证实存在取尾段限制 | 人工界面与机器回报分别验收；不能混称成功 |
| 新prompt pending与旧内容交付并发 | 原版REAL-9/12已证实错归轮、错序或丢失；订阅屏障不能避免 | 需宿主原子协调或带归属/源序的历史交付能力；见HOST_CONCURRENT_DELIVERY_GATE.md |
| 已有状态 plugin 行更新的位置、是否影响机器连续段 | 展示有同 ID 更新能力；组合行为仍需专门门禁 | 不能仅凭“卡片能更新”就承诺结果不被截断 |
| 原生通知是否影响机器结果 | `session.notice` 会转换为 timeline notification | 状态展示路径要测试；不能按固定频率堆通知 |
| 轮次结束/失败后的页面状态更新 | SDK允许状态类展示；本项目链路仍受 outcome/active 过滤 | 必须做完整链路测试，不只测 renderer |
| 当前错误 UI / Retry 结构 | 尚缺足够真实结构样本 | 用脱敏结构夹具及后续获批只读采样补证 |

门禁不是要求立刻改 Paseo，而是防止把当前不可能保证的部分写成已承诺交付。

## 3. 一套方案：原始事实优先，独立状态，有序内容

保留现有链路：

`Chrome 扩展 → 本地 Broker → Provider → Paseo`

不另建事件平台、浏览器服务或第二套正文。

### 3.1 采集先选规范来源，再做转换

一次读取分为两个阶段：

1. 纯读取候选，验证会话、文档、消息身份、公开性、归属及原生来源位置。
2. 保留原生消息级完成证据；已完成项整体交给接收端做一次格式适配，不在浏览器做跨帧正文转换。

只有结构证明是被规范消息覆盖的副本，才能排除。排除必须发生在确定正文和完成标志之前。不能机械地用“顶层 > reasoning > view > DOM”混排不同维度，也不能取最长文本、按相同字符串去重或任意挑一份冲突数据。

没有权威依据的冲突，记录在对应消息上；不能让整个页面不可读。短快照也不能仅凭更短就当作陈旧，完成标志只能来自同一个已验证来源。

### 3.2 内容与状态分成两个独立结果，不是两个应用

**内容批次**：当前锚点下的所有新消息/更新，包含正文、公开过程、工具、媒体；带原生 ID 和来源位置。按源序处理，不再只取最后一个 assistant，也不再“先所有 reasoning，再所有工具，最后正文”。

**页面状态**：可见原生提示、控件、执行证据、可读性和同步健康，独立采集、独立更新。正文失败不能挡住这一结果。

一个通道读不到，只将该通道标为 unavailable/partial；不返回一个整页 `messages: []` 来抹掉其它已经读到的事实。

来源顺序未证明、旧位置的内容迟到或宿主不支持重新排序时，不发明顺序。能从完整批次补齐的先补齐；不能补齐的标缺口，不能算保真通过。

### 3.3 三类状态正交记录

在现有持久化中增加必要字段，不改变现有 turnId 含义：

| 类别 | 保存什么 | 不能据它推断什么 |
| --- | --- | --- |
| 页面事实 | 错误原文、提示原文、按钮标签/可见性/可用性、出现/变化/确认不再显示的时间 | 提示消失不等于任务恢复或完成 |
| 原生执行 | 已验证的原生状态、来源、最后确认时间；无法确认则 unknown | Stop 消失、空白页、断连不能证明停止 |
| 同步健康 | 正常、延迟、局部受阻、观察丢失；受影响对象、原因及覆盖缺口 | CIP failed/idle不能冒充原生终止 |

“不可读”和“确认不存在”必须不同。保留最后已知状态时，必须带上时间和过期标记，不冒充当前状态。

每份观测沿用已有绑定身份，并增加必要的观测序号/版本信息，拒绝旧文档或旧顺序的迟到事件。只为防重与恢复增加元数据，不重造身份系统。

### 3.4 原生错误原文独立于正文

从已绑定页面的可见错误区域、错误边界和控件区域采集，不靠少数预设英文错误句判断一切。

- 原文及换行保留；未知提示照样显示为“网页提示，未分类”。
- Retry 等按钮记录实际标签、可见性和是否可用，只读不点击。
- 有对应消息/轮次归属证据的，标注所属对象；只有页面级证据的，明确显示为页面级，不硬挂到当前回答。
- 正文中引用的错误句、代码块里的 Retry 不当成原生故障或按钮。
- 页面空白、只有错误和 Retry、没有可读消息 ID 时，页面级观察仍可工作。
- 无法证明已绑定页面身份时，只报告绑定/观察不可用，不抓取其它标签或其它对话来填空。
- 扩展不可进入的浏览器内部错误页等情况，只能明确报告不可观测，不能编造网页原文。

预期显示形式（示意，不是现场原文）：

> 网页提示（原文）：……
>
> 网页可见操作：Retry，可用。
>
> 原生执行状态：待确认。
>
> CIP 同步：提示及控件已同步；正文读取受阻。
>
> 最近确认：……

正文异常不得覆盖上面的网页原文。截图方案继续搁置。

### 3.5 观察生命周期不能等同于一轮正文生命周期

`/active` 当前排除已有 outcome 的轮次，背景恢复和 monitor 又依赖这条链。仅在 content.js 不清 monitor 不够，必须连同绑定枚举和 Broker 验证一起处理。

- 已绑定、尚未结束观察的页面，在 Paseo 一轮失败/结束后仍可进行受限的只读状态观察。
- 同步失败不自动 Stop，不假装原生已停，也不能将未知执行状态当作可安全开始新执行的证据。
- 观察丢失可以报告跟踪失败，但独立页面观察仍能恢复；重连只补观察，不重发 Prompt。
- 绑定失效、明确归档/结束跟踪等情况按现有安全边界停止观察，不永久扫描所有浏览器页面。
- 页面恢复、内容恢复、原生执行恢复分别确认，不能由一个提示消失推导三者都恢复。

Retry 可能沿用原用户 ID。先依据实际新 assistant ID/原生执行证据识别变化；不伪造新用户消息。是否需要新的 Paseo 执行轮次，要经过真实结构及宿主生命周期门禁，不能先靠改 turnId 解决。

### 3.6 Broker 保存发布事实，页面缓存只保存工作状态

- 规范消息的已发布基线/游标及失败归属由 Broker 持久保存，承接重载/重连。
- 页面端只保留必要交付状态；浏览器流式解析缓存已删除。不能靠遗忘已存版本重新发布旧数据。
- 历史错误留在所属消息/轮次，不阻断新的正常内容或状态。
- 重新计算结果必须与已发布事实对账，不把加载历史当成首次生成，不给旧任务再次发送提示。
- 无声丢弃公开摘要修订、静默丢工具详情、把未确认的工具统一标取消等路径都需要检视；没有原生终态证据，就保存“结果未确认”，而非发明成功/取消。

### 3.7 Paseo 展示尽量复用现有区域

- 正文保留原生消息身份，每条完结即整体提交；不要求逐字，不等待整轮。确证中断时收录可读的已生成部分，并标为 interrupted。
- 工具/公开过程/媒体使用对应内容类型与源序。
- 扩展现有状态行/通知能力，分开原生事实与同步健康，不新增第二份正文卡片。
- 同一状态更新原位，不把每次读取追加成新消息。
- 状态卡升级须保留旧版本历史渲染；旧客户端不支持新类型时必须明确说明能力不足，不能走“图片已生成”等不相干的通用回退。
- 单条正文的原生 item.completed 即可交付，包括final_answer频道；**任务完成**仍须同一锚点的规范最终项完成、原生轮次终态和已存版本核验。单条completed、Stop消失或静默不能替代任务终态证据。

## 4. 有界不等于可以悄悄丢内容

保留内存、批次和传输上限，但优先用分页、分块和累计游标补足可读内容；不简单把上限无限调大。

区分三种情况：

1. 还没加载/采集到；
2. 已采集但超过单包显示上限，能够继续加载；
3. 受来源或宿主能力限制，当前无法完整呈现。

第2类应补齐；第3类必须显式说明，且不能计为完整保真通过。必要脱敏要明确标识，不宣称字节级原文一致。隐藏分析、凭据、账号菜单及其它对话不属于同步范围。

采集采用事件触发与周期对账结合，避免只靠固定轮询漏掉同批多条消息。Chrome 后台节流、虚拟化/临时卸载及跨源内容不可读必须专项验证，不能承诺捕获所有未来页面结构或每个短暂 UI 帧。

## 5. 实施顺序与文件边界

| 阶段 | 要做什么 | 完成门槛 |
| --- | --- | --- |
| P0 能力与事实门禁 | 固定版本，保留现有宿主红例；补原生错误/Retry结构证据与接口组合验证 | 先写清能交付/不能承诺的范围；不归罪模型改字 |
| P1 修确定回归 | 先规范来源/排除副本，再转换；旧错误隔离；正文失败不清空全部观察 | 现有3个事故红例转绿，且完整消息保真/错误拒绝安全断言仍成立 |
| P2 独立页面观察 | 分开原生状态、页面提示与同步健康；贯通失败后/重连后的只读观察 | 正文异常、空白页和仅错误页时仍能显示可读原文和控件状态 |
| P3 内容保真补齐 | 全部新消息与工具/媒体按源序批量同步；修摘要修订/超限的静默路径；分页分块 | 原生与Paseo逐项对账，不能只检查最后一句 |
| P4 恢复与发布验收 | 同ID Retry、后台节流、断连/重载、容量、历史重开、桌面/紧凑布局、回滚兼容 | 获批真实验收后才重新发布；界面与机器回报分开出结论 |

主要修改位置仍在现有模块：

- 规范来源/正文：`extension/upstream/cos-shell-public.js`、`upstream/cos-picker-main.js`、接收端 `shared/public-prose.mjs` / `server/message-delivery.mjs`；生产 `public-prose-main.js` 已移除。
- 独立观察与顺序：`dom-adapter.js`、`content.js`、`upstream/cos-activity-main.js`。
- 恢复与持久事实：`background.js`、`server/runtime.mjs`、`broker.mjs`、`native-timeline.mjs`、`activity.mjs`、`provider.mjs`。
- 展示与校验：`shared/activity.ts`、`client/native-activity.tsx`及相关注册。

使用现有链路，不为这次需求另建通用事件平台。用户已批准开始离线实现；进展与未通过项见实施文档。

## 6. 验收矩阵：能推翻方案，而不只是证明正常样例

| 情形 | 核心断言 |
| --- | --- |
| 只增正文，中文/Unicode/公式/围栏/长行 | pending 不发正文，中间完成消息不等整轮；接收端一次适配、最终原文投影与 Paseo 展示一致，无重复/漏字 |
| 同ID副本相同/较短/不同/提前completed | 被证明应排除的副本不修改缓存或完成标志 |
| 真实非前缀修订，公开摘要修订 | 不整段重复、不静默丢；当前宿主不支持的部分明确不通过 |
| 多条assistant及工具/媒体在同次读取出现 | 不只发最后一条；按原生顺序、身份和完成标志对账 |
| 旧错误＋正常新轮；40条历史错误 | 新轮和状态独立可读；回收不抹掉发布事实 |
| 限额、未知报错、错误页＋Retry、空白＋Stop | 可读原文与控件状态保留；无任何自动点击；未知不变成停止 |
| 提示消失、临时卸载、真正恢复 | 三者不混同；不能从缺失推断成功 |
| 第9条公开摘要、第33个工具、长详情与超过12步骤 | 可补齐的分批补齐；任何缺口可见，不阻塞正文/状态 |
| 内容及状态RPC分别失败、断连、重载 | 单通道错误不扩大；过期状态标记清楚；不重发操作 |
| 同用户ID Retry、新用户ID外部继续 | 以实际身份/执行证据识别；不伪造用户消息或随意新建轮次 |
| 后台页面长时间运行/节流 | 测量实际观察时效；新鲜度真实，不把旧图景冒充实时 |
| 源中未确认的工具结果 | 不伪造完成或取消 |
| 状态原位更新、通知/工具穿插、轮后更新 | UI正确与机器结果完整分别验证；后者不通过不能宣称已修 |
| 归档/重开及回滚 | 不丢历史、不重发、不盲目覆盖新状态；旧新协议能力明确 |
| 新提示在旧内容待交付时到达/启动失败 | 旧消息不归新轮、不排在新user后、不被stagedEvents清理丢弃；原版真实类红门禁保留 |

新增风险如“副本提前完成”“错误缓存耗尽”“时间线超限阻断”目前是代码检查推断，先写红例确认，不冒充现场已复现首因。已有首发原始两帧缺失，必须明确保留证据边界。

## 7. 委员会收敛与当前基线

Dario（Claude/high）与 Piltman（Pi/max）进行了两轮只读评审。主助手核对原版代码后，收敛为上述主线。

已撤回的建议：

- 追加一份带“已修订”说明的新全文；它仍然重复，机器结果也可能拼接新旧两份。
