## 已确认的问题

### P0-1：网页有正文，但采集器返回整份对话不可读

- 10:29:46、10:29:49、10:29:53 三次独立调用扩展现有 `cip-cos-transcript-ask-v2` 只读接口，均得到 `available=false`、`messages=[]`、`error=TRANSCRIPT_UNCONFIRMED`。
- 同时 DOM 可读到第一轮最终回答“NAS 管理证书自动续期已正式上线”和第二轮进度。
- CIP 的 `history` 中没有一条 assistant_message，故不存在“已保存但只在 Paseo 隐藏”的证据。
- 第一轮最终回答明确缺失；早期工具曾正常回传而进度正文始终为零，说明还需单独核对 public commentary 的可见性/完成条件，不能假定修好最后一次异常就补全所有进度。

**根因已定位到采集层，但具体抛错分支尚未确证。** MAIN catch 会把未列入允许名单的异常统一变成 TRANSCRIPT_UNCONFIRMED。代码中的 TRANSCRIPT_LIMIT、TRANSCRIPT_CONFLICT 等内部抛错均可能被压成同一码，不能据当前错误就断言是“网络慢”或“400 项上限已触发”。

### P0-2：历史轮次与当前轮次共用一次全局解析，缺少故障隔离

- `publicTranscript()` 一次遍历多个轮次，外层单个 try/catch；一个轮次抛异常会让整份结果变成 0 消息。
- 新一轮发送回执已经确认，但它立即同样进入 TRANSCRIPT_UNCONFIRMED，说明“送得出去”不等于“回得来”。
- 已验证整体投影失败；“究竟是旧轮次污染新轮次，还是两轮分别不受支持”尚未取得独立的 MAIN 原生数据来区分。不能无证据地放宽身份核验。
- DOM 结构已变化：没有传统 data-message-id；使用 data-turn-key、fallback-turn-* 搜索布局键与真实 data-chatgpt-search-message-ids。最终回答搜索标记中同一 ID 出现两次。布局键不能充当消息身份，重复搜索标记也不能直接当两条回答。

### P0-3：读取失败与停止控制耦合，错误被扩大成本轮失败

- 10:24:36 的 Stop 命令失败，原始错误为 TRANSCRIPT_UNCONFIRMED；CIP 随后写入 STOP_UNCONFIRMED，Paseo 记录停止未确认。
- `dom-adapter.stop()` 先调用 `state(nativeMessageId)`；正文解析出错时停止路径也无法正常核验。不能因正文暂不可读就把网页完成/停止情况推断出来，更不能绕过目标身份乱点 Stop。
- 第一轮页面最终有完整回答，却在本地留下失败状态。这个失败表示跟踪/停止未确认，不等于网页开发任务失败。
- 授权上报也在 `D.state()` 成功之后才执行。因此正文解析失败会挡住授权读取，这是**代码确认的风险**；本次取证期间网页无授权框，不能说当前又卡在授权。

### P1-1：开始下一轮后，上一轮遗漏正文没有补齐路径

- 10:24:41 新 Send 成功，`session.turn` 已切换到第二轮；第一轮仅剩用户、状态卡、工具历史。
- 正常观察按当前 nativeMessageId 切出本轮答案，不能自动把网页第一轮已存在但从未入库的最终回答补回。
- 因此“当前轮以后恢复同步”不代表旧答案已找回。应独立记录每个原生消息/轮次的采集与交付情况，而非只围绕一个 session.turn 判断完整性。

### P1-2：工具/摘要/步骤存在固定截断，缺少完整性声明

- `projectTurnMessages` 的 400 项/深度上限是另一项可能的长任务解析风险；**未证明它就是本次抛错源**。

### P1-3：授权等待工具残留“运行中”，状态卡自相矛盾

- 现有过滤仅识别 `codex_apps · <app>.approval_wait` 分支，不能完整覆盖 `mymac · approval_wait` 或 asdk_app 命名变体。

### P1-4：连接恢复、内容恢复、任务结束的表达与证据混在一起

- 10:21:32 出现“已恢复网页跟踪”，但解析错误没有解除、正文仍为 0。这里恢复的是连接/观察绑定，不是内容回传。

## 应如何重新划分同步职责（不修改 Paseo）

1. **发送**：排队 / 已尝试 / 已确认送达 / 结果未确认。Send 不因其他同步失败而重试。
2. **网页任务**：运行 / 等授权 / 已结束 / 状态未知；必须带原轮次身份和最后确认时间。网页任务结果与本地同步结果分开。
3. **正文与产物**：按原生消息 ID 分别记录可见、完整、已入库、已投递、宿主是否确认；有遗漏/截断就明确标出，不能把“扩展在线”当作完整同步。
4. **工具与授权**：独立于正文读取失败，沿真实调用/授权身份更新；不根据名字去重、不把等待步骤当正在执行的真实工具。
5. **历史补齐**：新轮次不覆盖旧轮次的待同步清单；读取旧答案不等于重发旧任务。正文、进度、工具同源顺序需各自验证。
6. **配置**：本轮实际配置与下轮待应用配置同时可辨，不把保存当作已应用。

优先级：先查清真实采集异常并补齐旧答案 → 拆开正文与控制/状态依赖 → 去除静默截断、修正 approval_wait → 区分当前配置/下一轮配置 → 再决定产物和恢复卡片覆盖范围。
