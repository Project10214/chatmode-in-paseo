# Chrome 是否只是中转、谁保存聊天记录：核实

2026-10-17。前半部分保留授权实现前的存储审查，描述当时流式候选；**当前实现以文末更新及FAITHFUL_SYNC_IMPLEMENTATION.md为准**，不能把旧转换器说成仍在生产候选运行。首次审查仅源码和临时Store实验；后续已获离线实现授权，始终未读取真实正文或操作现场会话。

## 结论

1. 此前路线确实在追求“已经发出的正文前缀不被后续加工改掉”，但实现并不是 Chrome 纯搬运：浏览器里仍有有状态的 Markdown 解码、前缀缓冲、完成冻结与错误保持。
2. Chrome 没有在本项目的持久存储路径中维护完整的 **ChatGPT 回复历史数据库**。有回复相关的内存缓存，也有持久化控制命令账本；二者不能混称。
3. Chrome 的命令账本保存整个命令，因而可能保留用户发送正文。不能说 Chrome 完全不保存任何文字。
4. 真正保存完整会话历史副本的是本机 **CIP 服务端插件** 的 `state.json`。它与 Paseo 宿主实际接收的时间线不是同一份存储。此前用“插件的小本子”概括 Chrome 和这份服务端文件，表述不准确。
5. 本机 `/event` 返回 accepted 不证明 Paseo 已保存/展示，甚至不必证明该正文已被采纳。本轮用真实 Broker 和临时 Store 实测了这一边界。现有开发尚未实现用户所说的“原生消息 → Paseo 最终记录”的完整逐项对账。

## 当前实际链路

```text
ChatGPT 当前页面的公开信息
  → Chrome 页面脚本：读取、格式转换、临时缓存、决定是否发送
  → Chrome 后台：绑定/权限检查，转发 /event
  → 本机 CIP 服务端：state.json 中的会话历史、发布基线及控制状态
  → Provider：timeline.item 事件
  → Paseo 宿主：自己的时间线处理、历史读取和界面渲染
```

CIP 服务端运行在 Paseo 的插件工作进程中，但 `~/.chatmode-in-paseo/state.json` **不是 Paseo 宿主聊天数据库**。宿主源码存在内存时间线以及可选 durable timeline 接口；本轮没有检查实际宿主数据库表、配置或用户消息，不据此断言其实际存储类型。

## 存储与缓存核对

| 位置 | 实际保存内容 | 生命周期/用途 |
| --- | --- | --- |
| `extension/public-prose-main.js:14,31,104–182` | 由该转换器处理的 DIL 原生消息的 raw、转换后 text、语法状态、完成标志、错误；候选增加独立失败记录 | 页面 JavaScript 内存 Map。路由变化/pagehide 清理，非 IndexedDB 聊天库。用于增量解码和限制已发表投影的变化 |
| `extension/content.js:196–235` | 已提交的正文/工具指纹、lastText、局部错误等 | 当前 monitor 的内存。用于重复扫描时减少上报，不是最终宿主确认记录 |
| `extension/background.js:15–25,64–70,158–232,641–644` | chrome.storage 的配对配置、标签绑定、命令 ledger、升级/恢复元数据 | 持久控制记录，避免 worker 重启后再次执行 Send。ledger 保存 command，因此可能包含发送正文；确认未发送时清理正文，已确认记录在正常轮询中超过24小时清理 |
| `extension/background.js:754–764` | observation 经校验后直接转发到 `/event` | 此路径没有将 AI 回复写入 chrome.storage |
| `server/store.mjs:25,43–57`、`server/broker.mjs:885–910` | sessions.history、最后完整正文、控制/同步状态 | 本机 CIP 原子写入 state.json；正文按 `assistant:<turnId>:<nativeMessageId>` 更新 |
| `server/provider.mjs:288–295,392` | live timeline 事件，重开时从 CIP history replay | 把 CIP 的数据交给宿主，不是宿主实际持久化或显示的回执 |
| Paseo 0.11.4 `plugin-provider.js:1338–1358` | 每个 item.id 的前次全文快照 | 宿主会把全文转成追加片段；非前缀变化不是任意全文覆盖 |

以上 Chrome 存储类型在已部署 alpha.4.16/0.2.23 和未部署候选中均存在；本轮实现没有新增“Chrome 回复历史数据库”。网页自身的 ChatGPT IndexedDB/草稿缓存属于网站，不能与扩展存储混同，也不能因为本次核实去清理。

## “只增加”开发方向的核对

历史方案 `APPEND_ONLY_TEXT_PLAN.md` 第1–3节明确选了“语法边界逐步转换”，保留 CoS 最终解码行为。它**没有选择直接转发 fallbackMarkdown 原串**；直接转发路线当时的视觉等价性仍待验证。

已确认的合成反例是：

- 原始输入从 `公式 \(` 增长为 `公式 \(x\)`，前面原字没有变。
- 旧逐帧转换结果却不保持前缀关系。
- 当前增量转换器在这个例子上恢复前缀连续性，但仍然是一个有状态转换器，不是无处理的搬运器。

本轮重跑上述真实函数，结果：原始只增=true，旧解码结果只增=false，当前转换后只增=true，当前最终结果等于旧解码器最终结果=true。这只证明该例及转换器一致性，不证明所有 ChatGPT 内容总是只增，也不证明与原生界面的全部视觉语义相同。

此前“同一答案从2改3”是解释修改与追加的假设例子，不能当成现场 ChatGPT 确实改字的证据。实际已证实的源头回归仍包括：应排除的副本先进入浏览器缓存、历史单条错误扩大到整页失明。这些是内存处理/错误传播问题，不能称为 Chrome 聊天数据库损坏。

## 收到、保存、转交、显示，当前没有完整贯通

`server/broker.mjs::observe()` 处理本机事务后返回 `{accepted:true,active:...}`；Provider 下游事件没有在这个返回值里提供逐消息的宿主持久化/渲染确认。

隔离实验脚本：`../logs/storage-boundary-audit.mjs`；结果：`../logs/storage-boundary-audit.json`。仅临时 Store 和合成字符串，执行后清理。

1. 不附着任何 Paseo Provider/宿主会话，上报普通 snapshot，仍收到 accepted=true。
2. 同 ID 上报非前缀新正文，Broker 保留旧正文、记录 ANSWER_NOT_PREFIX，返回值仍为 accepted=true。
3. 本地回复记录只有1条；它与第二份被拒正文不相同。

因此当前 accepted 只能按“事件被本机处理”理解，不能把浏览器的发送缓存、CIP 落盘或这个返回值当作“Paseo 已正确收到并显示”。该证据不证明现场某一次具体传输丢失，也不代表本轮已修复确认链。

## 对“浏览器只做搬运”的判断

可收敛的职责是：Chrome 识别正确的当前会话及公开消息，携带原生身份、来源、格式和状态转发；不另建权威聊天历史，不自行改写/总结正文，不把缓存状态当作宿主完成事实。必要格式适配必须有依据并在明确的一处处理、验证，不把内部占位符或编码串直接冒充用户看到的内容。

“轻量中转”不等于完全零状态：配对绑定、命令防重发，以及未确认数据的最小暂存仍有用途。若完全不暂存，断网时出现又消失的网页提示无法保证补取；若连未确认数据都不持久化，浏览器退出后也不能承诺不丢这些瞬态信息。必要暂存不是第二套会话历史，不能以简化为由删除现有安全凭据或盲目重发任务。

消息的接收、采纳、落盘、宿主交付及实际对账应分别有证据。缺少宿主确认时必须是未知/待核对，不是成功。对账主体应在接收侧，仍须解决原有宿主能力门禁；删除 Chrome 缓存或再加一套编号不能代替这些工作。

本轮不把用户核实问题当作清除数据、迁移历史、部署或更改 turnId 的授权。原有两个宿主恢复红例与真实会话恢复要求继续保留。

## 后续审查：改为单条原生消息完结后提交，可以减少什么

这是用户提出的新候选取舍，不是已经切换的产品行为：正文改为逐条出现，工具/页面状态继续实时，不等待整个任务才发全部内容。当前只审查，不修改应用、不删除现有流式测试、不弱化保真验收。

按职责归类，**6类流式专属规则可删除，3组逻辑可收敛**。这是可审查的分组，不是机械if数量、净代码删除量或性能百分比。

### 6类删除候选

| 类别 | 当前位置 | 整条模式为什么不再需要 |
| --- | --- | --- |
| 逐字符扫描、提交游标与半个Unicode字符暂存 | public-prose-main.js::partial、resetLine | 不再发布未结束的字符片段；整条做正常文本校验 |
| 半行、反斜杠、行内语法的安全前缀等待 | partial、lineComplete | 未完成消息不交付正文，不必猜下个字符怎样改变解码 |
| 跨帧代码围栏/公式等待与超窗口重放 | lineComplete、entry.fence/math | 完结文本一次处理；单次格式转换本身的语法/资源边界仍保留 |
| 浏览器同时累积raw/text、逐帧前缀衔接及换表示重建 | newEntry、advance | 浏览器转交原生身份和当前完整数据；不维护第二套逐字演进的正文 |
| 已完成投影冻结、退回缓存正文、忽略迟到未完片段的专用分支 | advance.finished、current/has/inspect | 未完帧直接不交付；已完消息后续变化交给接收侧版本对账，不能永远忽略 |
| 解析器专属32项容量回收、400项永久失败墓碑 | update、entries/failures | 没有长寿命增量解析器就不需要这套表；真实错误与历史证据仍保留在对应消息上 |

最大的独立候选块是 **extension/public-prose-main.js，183行（含注释/空行）**。其中有7个跨帧语法字段：line/released/scanned/leading/held/fence/math，以及entries/failures两张Map。整条模式可整体替换这套状态机及接线；但仍要接通消息完结信号、单次必要格式处理和可靠交付，不能把183行说成已经实现的净删除量。

### 3组收敛候选

1. **完成前反复发送全文、多份“发过了”的判断 → 完结条目提交，接收侧按原生ID和内容版本对账。** 浏览器只留必要待交接数据/节流状态；确认后不反复交付同一版本，断连只补未确认数据，不把自己的缓存命中当作Paseo确认。
2. **边写边解码、最终再比一次 → 完结后一次必要格式处理。** 不盲目删除格式适配，也不能只以“等于旧转换器”冒充原生视觉正确。发布后的真实修订和旧的半段历史仍要核验，Broker的现有已发布前缀保护不能直接删。
3. **最后一条正文、静默等待与完成的交叉推断 → 明确的消息就绪和任务终态判定。** content.js中1000/4000ms的quietSince不再承担完成等待依据；心跳、断连检测、读取重试及传输期限不是同一类，不能一并删除。消息完成与任务结束仍分开。

### 必须保留的6类职责

- 规范公开来源、原生身份、会话/文档归属与隐私边界。
- 这条消息是否完整、内容是否可读，以及整个任务是否真正结束的独立证据。
- 可靠交接、断连补取、幂等数据重传；不能自动重发模型任务。
- 原生顺序、历史身份对账、迟到/修订检测；不能按谁先写完就随意乱序。
- 工具/媒体完整性、传输边界与可补齐的分块分页；不能默默截断。
- 配对、绑定、命令防重发、权限、队列与停止确认；状态/错误/按钮仍独立实时观察。

### 本次实际发现的接线缺口

用真实sourceFor及人工输入对比，原生commentary的completed从false变true、整个turn仍in_progress时，当前投影完全相同：status仍in_progress、end_turn=false。picker继续只传final。**现有final表示最终回答，不是“这一条消息写完”。** 因此只加if(final)会漏掉已经写完的中间发言；必须把已有原生消息完结证据沿链路保留下来，不能另发明静默时间规则来猜。

还必须覆盖明确停止/失败的情况：半条可见正文不能因为没正常完成就永远丢掉；有原生中断证据时，应整体收录当时的可见内容并标明中断，而不是宣称正常完成。当前content.js的stop分支会清monitor、Broker收Stop确认后会结束turn，整条模式不能原样沿用而遗漏最后内容。仅Paseo取消请求、停止未确认或断连不构成原生中断证据。

### 验证边界

- `../logs/completed-message-reduction-audit.mjs` / `.json`：真实生产函数、合成数据、无账号/宿主操作。
- 已复现消息完结信号在投影丢失；最终回答的任务终态保护仍有效。
- 6组文本/Unicode/公式/表格/代码/转义例子，一次解码与当前增量转换器的最终输出6/6一致。只是旧最终行为对照，不是原生界面等价、完整新链路或性能验收。
- 完成后再提交也不会自动修好两个旧Agent、宿主已结束轮次、晚到消息插入顺序或actual-Paseo确认。这些门禁继续保留，不再直接推导为必须新造ID。

建议正文主路径收敛为：**识别原生ID和归属 → 等此条完结/有明确中断且内容可读 → 整条交接 → 接收侧对账确认**。未确认保留待交接状态；工具、原生错误和执行状态不被正文等待阻塞。


## 2026-10-17 · 已授权实现后的更新（未部署）

规则减法已实施，不再只是建议：删除生产流式状态机及 manifest 加载；浏览器按消息级完整原表示交接，接收端一次适配和持久幂等。普通正文不再使用 snapshot；旧 snapshot 入口仅为兼容保留。历史研究/旧解析器测试明确标为 HISTORICAL，没有当成新生产覆盖。

新增回执区分 stored / unchanged / rejected，并核对原生消息 ID 和原样数据版本。拒收不再被 accepted 冒充正文保存；host 始终 unconfirmed。finalRevision 只能确认当前完整正文或等价完整表示，旧 interrupted 回执不能认证完成。待授权也不阻止已经完成的说明消息交付。

此处“整条”是消息，不是任务。pending 原表示仍可在浏览器内部读取；不作逐字语法处理、不向接收端逐字发布。源读取、隐私、归属、配对、防重发、最小交付记录仍存在。没有净删行数或性能百分比承诺，也没有把浏览器说成完全不存任何文字。

实际原版宿主生命周期实验见 [HOST_RECOVERY_EXECUTION_AUDIT.md](HOST_RECOVERY_EXECUTION_AUDIT.md)。已失败的前台轮次不能在同一宿主会话中盲目重开；新会话有订阅时序要求。更重要的是现有 session.close 在 CIP running 时会触发 Stop，所以不得把重载当成天然只读安全操作。线上未执行重开或恢复。

完整状态及剩余门禁见 [FAITHFUL_SYNC_IMPLEMENTATION.md](FAITHFUL_SYNC_IMPLEMENTATION.md)。

### alpha.4.19：宿主暂存也不是宿主保存

- Provider对未证明订阅的binding按稳定条目ID保留有序完整快照，重复观察不形成无限事件数组；固定notice同ID替换。实际Broker满1000行历史边界已验证，全部正文/工具保留。
- 不再有512条裸发或3064条超限丢弃警告。自然边界来自持久化身份、载荷预算和固定标记；32MB是Store序列化上限，不含JS对象包装/副本，不能报为Map精确内存上限。
- 队列只在内存：进程退出会失去其中的通知、生命周期与交付进度。正文仍在CIP历史，不等于真实宿主已回放，不能承诺重开必然补齐。
- 当前重新读到并重交已存版本才可精确清除该消息的拒收问题；旧receipt单独不能清当前拒收。
- 原版REAL-9/12进一步证明：即使已订阅并已发出，宿主新prompt pending仍可能错归轮或丢弃旧正文；因此host继续unconfirmed。见 [HOST_CONCURRENT_DELIVERY_GATE.md](HOST_CONCURRENT_DELIVERY_GATE.md)。
